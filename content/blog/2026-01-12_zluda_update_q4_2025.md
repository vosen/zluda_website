Llama.cpp support is now complete ([Full llama.cpp support](#full-llama-cpp-support)) and we made a lot of groundwork for Windows ([Better Windows support](#better-windows-support)) and to prepare for PyTorch ([ZLUDA now ships with bundled LLVM](#zluda-now-ships-with-bundled-llvm), [Compiler performance improvements](#compiler-performance-improvements), [ROCm 7 works now](#rocm-7-works-now), [PyTorch support underway](#pytorch-support-underway)).

# ZLUDA now ships with bundled LLVM

Historically, ZLUDA used AMD provided comgr library ("Code Object Manager API") that is installed on your system as part of ROCm. This library is a wrapper around LLVM. It mostly works fine, but comes with two caveats:
* AMD LLVM is often buggy and AMD does not backport LLVM fixes. If a user has a non-bleeding edge, "stable" LLVM bundled with ROCm then there's nothing we cand do about bugs in it. This is especially important for PyTorch as there are patterns in PyTorch GPU code that crash AMD GPU LLVM, purely because of bugs in AMDGPU target
* We can't do all the optimizations we want. While we try hard to emit as good as possible LLVM bitcode, ZLUDA compiler simply is not an optimizing, SSA-based compiler. There are certain optimizations that are relevant to Machine Learning workloads that are outside of our reach without custom LLVM optimization passes

We have wanted to ship a ZLUDA-patched LLVM for a long time. Now, as part of the work on llama.cpp and PyTorch we have finally did it and started shipping LLVM with ZLUDA. The ZLUDA side was merged in [#555](https://github.com/vosen/ZLUDA/pull/555) with required LLVM work done [here](https://github.com/vosen/llvm-project/commit/f83cd44622f6792d9f1672ce700ab10ee1c23f92) and [here](https://github.com/vosen/llvm-project/pull/1).

There's one downside to our new approach: LLVM is a massive project and building it is time consuming. Our automatic builds are mostly unaffected because we use sccache, but if you are compiling ZLUDA yourself, expect much longer build times. We recommend that users who want to try work-in-progress builds download prerelease binaries from Github. We build every merged pull request.

# ROCm 7 works now

ROCm 7 has been out for several months already, but we did not start working on it instantly. Partially, because we've been genuinely busy with all the issues described in this update, partially, because ROCm version updates can introduce hard breaks, which take a long time to resolve. We want ZLUDA to work equally well with both ROCm 6 and ROCm 7 without us having to maintain two separate builds. ROCm 5 to ROCm 6 was a difficult upgrade with many breaking changes. Granted, most of them were necessary and made sense, but it was still a lot of extra work. Thankfully, ROCm 7 is mostly backwards compatible. There are two functions that made broke ABI, but ZLUDA did not use them and they were clearly marked as experimental.

The problem this time comes from some unfortunate packaging choices and interactions on Windows. On Windows, AMD graphic driver ships with *all* ROCm 5, ROCm 6 and ROCm7 runtimes at the same time (respectively `amdhip64.dll`, `amdhip64_6.dll`, `amdhip64_7.dll`). Which is fine, backwards compatibility is good. The problem is with the performance libraries. For some reason the latest official version of performance libraries on Windows is 6.2. That is more than a year old and relies on amdhip64_6.dll. This can lead to some unfortunate interactions. ZLUDA works with either `amdhip64_6.dll` or `amdhip64_7.dll` and will prefer to load `amdhip64_7.dll`. It's possible for ZLUDA to launch, load `amdhip64_7.dll` and later load a performance library which in turn loads `amdhip64_6.dll`. Having both ROCm 7 and ROCm 6 runtimes loaded in a process at the same time and trying to interopate between them simply does not work and leads to mysterious crashes.

Since we can't travel in time we settled on the second best solution: preloading performance libraries into the process and then scanning the process for the presence of either `amdhip64_6.dll` or `amdhip64_7.dll`. See details in [#579](https://github.com/vosen/ZLUDA/pull/579). This makes ZLUDA startup slightly slower, but should be fine.
We might consider shipping ROCm performance libraries with ZLUDA in the future. What do you think?

# Too slow for katago

As mentioned in the last update, we are at the point where we have a mechanism for collecting execution traces that does not require you to be a developer. And happily, some of you blessed us with traces for your favorite application. One of those apps was katago: a ML-based library for playing the game of go. The trace told us two things: firstly, majority of the required CUDA support for katago is already there, secondly what's missing (cuDNN support) is on our priority list. Might as well work on it.

Katago uses CUDA in a pretty straightforward way, but it excersises some features of cuDNN for which there is no direct ROCm support. After some hard work on workarounds in PR katago finally ran! And it did run embarassingly slow, thousands of times slower than NVIDIA GPUs. Quick investigation uncovered the root of the issues: certain katago operations have a very slow, naive implementation in MIOpen and optimized implementation in cuDNN. Sadly, there's nothing we can do about it, hopefully AMD will one day optimize those convolutions and make AMD GPUs a viable target for katago.

You can see the whole story here [#541](https://github.com/vosen/ZLUDA/pull/541) and please keep sending us traces. While we might not be able to work on them right away, they are important for prioritization and debugging.

# Better Windows support

For the most of modern ZLUDA history Windows support was an afterthought. While we make sure that every change compiles on Windows the loader that injects ZLUDA into an executable was in a very poor state. In the last update we have asked you to share traces from your favorite CUDA application and you sent us mostly Windows ZLUDA traces. Or at least attempted to do so with how bad ZLUDA loader was. This forced us to face the reality: either we fix the loader or we get no traces.

This led to a major (19100 lines added, 2377 lines removed) PR [#550](https://github.com/vosen/ZLUDA/pull/550) which brought `zluda.exe` on Windows to a more acceptable quality and allow ZLUDA to work as well as on Linux.

# Compiler performance improvements

One of the ways PyTorch is different from other CUDA projects is that it ships fairly big (in the order of megabytes) PTX modules. This is poses a challenge to ZLUDA compiler that is tuned to produce decent quality code, but not to run fast. In particular there was one compiler pass: `instruction_mode_to_global_mode` that could take 60% of the total compilation time. After [#552](https://github.com/vosen/ZLUDA/pull/552) was merged this time went down to take less than 1% with majority time being now spent in the LLVM.

Additionally we have added an experimental precompilation tool that can scan a directory, detect all CUDA binaries and precompile all the PTX modules. This uses all the cores on your machine, making it much faster than compiling one-by-one that is done by the CUDA runtime. The effect will vary application-by-application: there are applications out there that will try to load (and compile) every GPU kernel possible, even if it's not being actually used. There are also applications out there that will compile only strictly used subset of kernels required by a given workload. In our experience, the former category is much bigger than the latter.

# PyTorch support underway

We are hard at work on PyTorch. It's impossible to support every PyTorch configuration and every project built on top of it. Our first goal is vLLM and for that purpose we've been ladning multiple small PRs that make vLLM on ZLUDA run further an further. See recent PRs: [#580](https://github.com/vosen/ZLUDA/pull/580), [#583](https://github.com/vosen/ZLUDA/pull/583), [#585](https://github.com/vosen/ZLUDA/pull/585), [#590](https://github.com/vosen/ZLUDA/pull/590), [#596](https://github.com/vosen/ZLUDA/pull/596) and more.

Since we don't have too much PyTorch support to show yet and since we've made many big changes (buindling LLVM, ROCm 7 support) there is no new major release, but we encourage you to take prelease builds out for a spin (and report any problems).
